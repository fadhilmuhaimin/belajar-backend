## Kenapa ini ada

Deploy pertama Raka: `ssh` ke server, `git pull`, build, lalu restart. Prosesnya sepuluh menit, dan setiap kali ada yang berbeda.

Suatu malam, versi Go di server ternyata lebih lama dari laptop Raka, dan build gagal di tengah. Server sudah dihentikan, tapi binary baru belum ada. Rekeningo mati 40 menit sampai Raka berhasil membangun ulang versi lama dari Git.

Masalahnya bukan di kode, tapi di cara mengirim kode. Raka butuh deploy yang sama setiap kali, dan cara mundur yang tidak butuh membangun ulang apa pun.

## Cara kerjanya

**Build sekali, jalankan di mana saja.** Image container berisi binary dan semua dependensinya. Image yang sama dijalankan di staging dan production. Build dua tahap membuat image akhir kecil: di lab, 28,9 MB.

<Snippet file="labs/api-t1/Dockerfile" region="docker" lang="dockerfile" />

**Konfigurasi dari environment, bukan di image.** Alamat database, secret, dan nama environment diberikan saat container dijalankan. Prinsip ini dari [The Twelve-Factor App: Config](https://12factor.net/config): konfigurasi berubah antar-deploy, kode tidak. Secret yang tertanam di image ikut tersebar ke semua orang yang bisa menarik image itu.

**Fail-fast dan health check.** Aplikasi memeriksa konfigurasi wajib saat start, dan menolak jalan kalau salah. Endpoint `/sehat` memberi tahu deploy bahwa versi baru siap:

**Rollback = jalankan image lama.** Rollback cepat karena tidak ada yang dibangun ulang. Syaratnya dua: image lama masih disimpan, dan skema database masih cocok dengan kode lama.

Syarat kedua inilah yang sering terlupa. Migration yang menghapus kolom membuat kode lama gagal walau image-nya benar ([[B4.2]]).

**Urutan pipeline Rekeningo Tahap 1:** test → build image → migration → jalankan image baru → health check → selesai, atau rollback. Di Tahap 3, satu instance diganti dua instance dengan rolling deploy, supaya downtime 0,2 detik di atas menjadi nol.

## Di stack lain

Yang sama di semua stack: artefak build yang tetap, konfigurasi dari environment, health check, dan rollback ke artefak lama. Yang berbeda: bentuk artefak dan health check bawaan. Baris di bawah dicek ke dokumentasi dan tidak dijalankan, kecuali Go.

| Stack | Artefak yang di-deploy | Health check bawaan |
|---|---|---|
| Go | Satu binary statis di image minimal (dijalankan di lab) | Tidak ada; tulis sendiri seperti `/sehat` |
| Express | Kode + `node_modules` di image Node | Tidak ada; tulis sendiri |
| Laravel | Kode + `vendor` di image PHP-FPM, biasanya dengan web server di depannya | Ada: route `/up` ([Laravel: Deployment](https://laravel.com/docs/12.x/deployment)) |
| Django | Kode + paket Python, dijalankan server WSGI/ASGI | Tidak ada di inti Django |
| Spring | File JAR di image JVM | Ada: `/actuator/health` lewat Actuator ([Spring Boot](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html)) |
| Supabase | Tidak ada server sendiri; yang di-deploy migration dan Edge Function | Dikelola platform ([Supabase: Deployment](https://supabase.com/docs/guides/deployment)) |

Satu perbedaan yang terasa di downtime: binary Go di lab siap dalam hitungan milidetik. Aplikasi JVM atau aplikasi yang memanaskan cache saat start bisa butuh beberapa detik. Dengan satu instance, waktu start itu langsung jadi downtime.

## Trade-off: kapan pakai apa

| Cara deploy | Kelebihan | Kekurangan |
|---|---|---|
| `git pull` + build di server | Tanpa alat tambahan | Hasil build bisa berbeda; rollback berarti build ulang |
| Image + satu instance (Tahap 1) | Artefak tetap, rollback cepat | Ada downtime singkat di setiap deploy |
| Image + dua instance + rolling deploy (Tahap 3) | Tanpa downtime | Butuh load balancer dan aplikasi stateless |

## Cek diri

**1.** Rollback ke image v2 berhasil, health check 200, tapi semua request profil error `column "telp" does not exist`. Apa yang terjadi?

<details class="success">
<summary>Jawaban</summary>

Deploy v3 sudah menjalankan migration yang menghapus atau me-rename kolom `telp`. Image v2 masih membaca kolom itu. Rollback kode tidak membatalkan migration. Karena itu migration harus kompatibel mundur: hapus kolom hanya setelah kode yang memakainya sudah tidak mungkin di-rollback ([[B4.2]]).

</details>

**2.** Jelaskan kenapa aplikasi sebaiknya menolak start kalau `TOKEN_SECRET` kosong, bukan memakai nilai bawaan.

<details class="success">
<summary>Jawaban</summary>

Dengan nilai bawaan, aplikasi tampak sehat tapi menandatangani token dengan secret yang diketahui siapa pun yang membaca kodenya. Kesalahan konfigurasi jadi celah keamanan yang tidak terlihat. Dengan fail-fast, kesalahan langsung terlihat di log dan health check, lalu deploy di-rollback.

</details>

**3.** Health check hanya mengembalikan `200` tanpa memeriksa apa pun. Apa yang terlewat?

<details class="success">
<summary>Jawaban</summary>

Instance yang tidak bisa menghubungi database tetap dianggap sehat, dan deploy dinyatakan berhasil. Health check di lab memanggil `PingContext` ke database supaya kegagalan koneksi terlihat.

</details>

## Saat me-review kode AI, cek ini

- [ ] Tidak ada secret, password, atau URL database di Dockerfile, kode, atau file yang ikut ke image.
- [ ] Konfigurasi wajib diperiksa saat start, dan aplikasi berhenti kalau salah.
- [ ] Ada health check yang memeriksa ketergantungan penting, minimal database.
- [ ] Image diberi tag versi yang tetap, bukan hanya `latest`, supaya rollback tahu harus ke mana.
- [ ] Migration di deploy ini tidak merusak kode versi sebelumnya.
