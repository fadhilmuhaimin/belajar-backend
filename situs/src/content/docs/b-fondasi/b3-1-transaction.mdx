## Inti

Transaction menjadikan beberapa perintah database satu unit: berhasil semua, atau batal semua. Tanpa transaction, tiap perintah langsung permanen. Kalau langkah kedua gagal, langkah pertama tidak ikut batal.

<WidgetLama nama="arsitektur" tahap={1} />

## Lihat sendiri

Di Rekeningo, Budi mengirim Rp70.000 ke Ani. Server menjalankan dua `UPDATE` berurutan. Saldo Ani dibatasi maksimal Rp1.000.000, jadi `UPDATE` kedua pasti gagal.

Kedua panel menjalankannya di SQLite sungguhan, langsung di browser. Tebak dulu hasilnya, baru jalankan.

<WidgetLama nama="runsql" src="data/b3-1-transfer.json" />

Setelah itu, centang **Ubah satu hal** lalu jalankan ulang. Kedua panel jadi sama persis. Transaction tidak mengubah apa pun saat semua langkah sukses. Ia hanya berpengaruh saat ada yang gagal.

## Kenapa ini ada

Minggu ketiga uji coba Rekeningo. Jam makan siang, Budi mengirim Rp70.000 ke Ani untuk membayar makan siang. Saldo Ani sudah Rp980.000 dari penjualan pagi, dan akun toko di versi MVP dibatasi Rp1.000.000 (aturan fiktif cerita ini).

Server mengurangi saldo Budi, lalu `UPDATE` ke saldo Ani ditolak constraint. Budi melihat saldonya turun Rp70.000, tapi Ani tidak menerima apa pun. Sore itu Budi menulis ke Sinta: "Saldo saya hilang Rp70.000."

Raka membuka database dan menemukan dua `UPDATE` yang berjalan terpisah, tanpa transaction. Perbaikannya kecil: bungkus keduanya dalam satu transaction. Penyebab gagalnya bisa macam-macam, mis. constraint, koneksi putus, atau server di-restart saat deploy. Transaction melindungi dari semuanya.

Kalau kamu pernah memakai `database.transaction((txn) async { ... })` di [sqflite](https://pub.dev/packages/sqflite) atau [`withTransaction { }`](https://developer.android.com/reference/kotlin/androidx/room/RoomDatabase) di Room, konsepnya sama persis. Bedanya, di backend ada banyak user yang menulis ke database yang sama pada waktu bersamaan. Itu masalah Tahap 2, di [[B3.2]].

## Cara kerjanya

<figure class="bb-fig" role="img" aria-label="Alur transfer dengan transaction: BEGIN, UPDATE saldo Budi, UPDATE saldo Ani gagal, ROLLBACK, saldo kembali utuh.">
<ol class="bb-flow">
<li><code>BEGIN</code></li>
<li>Budi −Rp70.000</li>
<li class="is-warn">Ani +Rp70.000 gagal</li>
<li class="is-good"><code>ROLLBACK</code></li>
<li class="is-good">Saldo utuh</li>
</ol>
<figcaption>Tanpa transaction: langkah 2 permanen, Rp70.000 hilang.</figcaption>
</figure>

- **`BEGIN`** membuka transaction. Di PostgreSQL, perubahan sesudahnya belum terlihat oleh koneksi lain sampai `COMMIT`. Koneksi lain tetap membaca saldo lama, dan [[B3.2]] menunjukkannya dengan rekaman dua koneksi.
- **`COMMIT`** membuat semua perubahan permanen sekaligus.
- **`ROLLBACK`** membatalkan semua perubahan sejak `BEGIN`.

Sifat "semua atau tidak sama sekali" ini disebut **atomicity**, huruf A di ACID. Dokumentasi PostgreSQL mendefinisikannya begini: dari sudut pandang transaction lain, sebuah transaction terjadi seluruhnya atau tidak sama sekali ([sumber](https://www.postgresql.org/docs/current/tutorial-transactions.html)).

Satu hal yang sering terlewat: database tidak menutup transaction sendiri saat satu perintah gagal. Aplikasi yang harus mengakhirinya dengan `ROLLBACK`. Di panel After tadi, baris `ROLLBACK` berwarna mint dijalankan oleh kode aplikasi, bukan oleh SQLite.

## Trade-off: kapan pakai apa

| Situasi | Pilihan |
|---|---|
| Beberapa perubahan harus konsisten, mis. saldo + riwayat transaksi | Satu transaction |
| Hanya satu perintah SQL | Tidak perlu `BEGIN`. PostgreSQL membungkus setiap perintah dengan transaction implisit ([sumber](https://www.postgresql.org/docs/current/tutorial-transactions.html)) |
| Perlu memanggil API luar, mis. payment gateway atau kirim email | Jangan di dalam transaction. API luar tidak ikut di-rollback, dan koneksi database tertahan selama menunggu |
| Data tersebar di dua database atau dua service | Transaction biasa tidak bisa menjangkau keduanya. Butuh pola lain (outbox, saga), dibahas di [[B10.2]] dan [[D3]] |

Biaya transaction: selama terbuka, ia memegang satu koneksi dari pool (kumpulan koneksi yang dipakai bergantian, [[B2.5]]). Baris yang diubahnya juga terkena lock, jadi transaction lain yang mengubah baris yang sama harus menunggu. Transaction yang lama membuat request lain ikut menunggu. Lock dibahas di [[B3.2]].

## Cek diri

Jawab dulu di kepala atau di catatan, baru buka jawabannya.

**1.** Kode Go ini memakai `db.ExecContext` (bukan `tx.ExecContext`) untuk `UPDATE` pertama. `UPDATE` kedua lewat `tx` dan gagal. Berapa total saldo sesudahnya?

```go
tx, _ := db.BeginTx(ctx, nil)
defer tx.Rollback()
db.ExecContext(ctx, `UPDATE akun SET saldo = saldo - 70000 WHERE nama = 'budi'`)
_, err := tx.ExecContext(ctx, `UPDATE akun SET saldo = saldo + 70000 WHERE nama = 'ani'`)
```

<details class="success">
<summary>Jawaban</summary>

Total jadi Rp1.010.000, sama seperti panel Before. `db.ExecContext` berjalan di luar transaction, jadi langsung permanen. `tx.Rollback()` hanya membatalkan perintah yang lewat `tx`. Dokumentasi Go memperingatkan hal ini secara khusus: jangan memanggil method `sql.DB` di dalam transaction ([sumber](https://go.dev/doc/database/execute-transactions)).

</details>

**2.** Di Django, kamu menangkap `IntegrityError` **di dalam** blok `atomic()`, lalu menjalankan query lain di blok yang sama. Apa risikonya?

<details class="success">
<summary>Jawaban</summary>

Setelah error database, transaction sudah dalam keadaan rusak. Query berikutnya bisa gagal dengan `TransactionManagementError`. Dokumentasi Django menyarankan membungkus bagian yang boleh gagal dengan `atomic()` sendiri, lalu menangkap error di luar blok itu ([sumber](https://docs.djangoproject.com/en/stable/topics/db/transactions/)).

</details>

**3.** Jelaskan dalam satu kalimat: kenapa memanggil API payment gateway di dalam transaction itu ide buruk?

<details class="success">
<summary>Jawaban</summary>

Kalau transaction di-rollback, uang di payment gateway sudah terlanjur ditarik, karena API luar tidak ikut rollback. Selain itu, koneksi dan lock tertahan selama menunggu respons yang bisa lambat.

</details>

## Saat me-review kode AI, cek ini

- [ ] Semua perintah dalam satu unit kerja memakai objek transaction yang sama (`tx`, `client`, `DB::transaction`), bukan koneksi atau pool global.
- [ ] Ada jalur `ROLLBACK` yang pasti jalan saat error: `defer tx.Rollback()`, `catch` + `ROLLBACK`, atau closure framework.
- [ ] Error di dalam transaction tidak ditangkap lalu diabaikan begitu saja.
- [ ] Di Spring, exception yang dilempar adalah unchecked, atau `rollbackFor` diisi.
- [ ] Tidak ada panggilan HTTP atau API luar di dalam transaction.
- [ ] Nominal uang disimpan sebagai integer rupiah (`bigint`) atau `numeric`, bukan `float`/`double`.
