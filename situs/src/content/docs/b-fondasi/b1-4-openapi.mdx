## Inti

Kontrak API menulis bentuk request dan response dalam format yang dibaca mesin. Dengan OpenAPI, perubahan yang merusak app lama tertangkap di pull request.

## Lihat sendiri

Seorang developer mengganti nama field `saldo` menjadi `balance`. Output lint dan pemeriksaan kontrak di widget ini direkam dari alat sungguhan.

## Kenapa ini ada

Raka menulis backend dan app sendirian, jadi selama sebulan tidak ada salah paham. Lalu Sinta merekrut developer Flutter kedua.

Minggu pertama, developer baru itu bertanya: `saldo` di response integer atau string? `ke` itu id akun atau nomor HP? Error saldo kurang bentuknya apa? Jawabannya ada di kepala Raka, dan sebagian di pesan chat lama.

Raka juga mulai meminta AI menulis endpoint baru. Setiap kali, ia harus menjelaskan ulang bentuk JSON-nya. Satu dokumen yang menjawab semua pertanyaan itu, dan bisa dicek mesin, menghemat waktu untuk ketiganya.

## Cara kerjanya

**OpenAPI** adalah format standar (YAML atau JSON) untuk menulis endpoint, parameter, request body, response, dan cara autentikasi ([OpenAPI 3.1](https://spec.openapis.org/oas/v3.1.0.html)). Potongan kontrak Rekeningo untuk transfer:

Yang membaca file ini:

| Pembaca | Memakainya untuk |
|---|---|
| Developer app | Bentuk JSON dan error, tanpa bertanya |
| Generator kode | Membuat client Dart atau Kotlin, dan kerangka server |
| CI | Lint, dan menolak perubahan yang merusak client lama |
| AI | Spesifikasi yang tepat saat diminta menulis endpoint ([[F1]]) |

**Breaking change** adalah perubahan yang membuat client lama gagal. Rule of thumb dari sisi app:

| Perubahan | Breaking? |
|---|---|
| Tambah field opsional di response | Tidak. App lama mengabaikannya |
| Hapus atau ganti nama field di response | Ya |
| Tambah field **wajib** di request | Ya. App lama tidak mengirimnya |
| Ubah tipe field, mis. integer jadi string | Ya |
| Tambah endpoint baru | Tidak |

Rekaman lab, untuk dua perubahan:

<Snippet file="labs/b1-openapi/output/kontrak.txt" title="Output rekaman: labs/b1-openapi/output/kontrak.txt" />

**Spec-first atau code-first.** Spec-first: tulis kontrak dulu, lalu kode mengikuti (bisa di-generate). Code-first: anotasi di kode menghasilkan kontrak. Keduanya sah. Yang penting, kontrak disimpan di repo, dan CI membandingkan versi lama dengan versi baru.

## Di stack lain

Yang sama di semua stack: hasil akhirnya satu file OpenAPI. Yang berbeda: **dari mana file itu berasal**. Baris di bawah dicek ke dokumentasi masing-masing dan tidak dijalankan, kecuali yang ditandai.

| Stack | Cara umum mendapatkan kontrak | Sumber |
|---|---|---|
| Go | Spec-first: tulis YAML, generate kerangka server dan tipe | [oapi-codegen](https://github.com/oapi-codegen/oapi-codegen) |
| Express | Tidak ada bawaan; ditulis tangan atau lewat library | – |
| Laravel | Code-first lewat library pihak ketiga | [Scramble](https://scramble.dedoc.co/) |
| Django (DRF) | Code-first lewat library pihak ketiga | [drf-spectacular](https://drf-spectacular.readthedocs.io/) |
| Spring | Code-first lewat library pihak ketiga | [springdoc-openapi](https://springdoc.org/) |
| Supabase | Otomatis: PostgREST menyajikan OpenAPI di path root | [PostgREST: OpenAPI](https://docs.postgrest.org/en/stable/references/api/openapi.html) |
| Semua | Lint dan cek breaking change di CI (dijalankan di lab) | [Redocly CLI](https://redocly.com/docs/cli/commands/lint), [oasdiff](https://www.oasdiff.com/) |

## Trade-off: kapan pakai apa

| Pilihan | Kelebihan | Kekurangan |
|---|---|---|
| Tanpa kontrak tertulis | Tercepat untuk satu orang | Pengetahuan ada di kepala; perubahan yang merusak baru ketahuan di app |
| Code-first | Kontrak selalu sama dengan kode | Desain API terbentuk dari kebetulan implementasi |
| Spec-first | API didesain dan direview sebelum kode ditulis | File kontrak dan kode bisa tidak sinkron tanpa test kontrak |

Rekeningo memakai spec-first ringan: `openapi.yaml` di repo, lint dan oasdiff di CI. Kode belum di-generate, karena endpoint-nya masih sedikit.

## Cek diri

**1.** App v1.4 masih banyak dipakai. Endpoint transfer ingin menambah field `catatan` yang **wajib** di request. Aman?

<details class="success">
<summary>Jawaban</summary>

Tidak. App v1.4 tidak mengirim `catatan`, jadi semua transfernya akan ditolak. Jadikan opsional dulu, dengan nilai bawaan di server. Baru wajibkan setelah versi minimum app dinaikkan ([[E1]]).

</details>

**2.** Jelaskan kenapa lint OpenAPI saja tidak cukup untuk melindungi app lama.

<details class="success">
<summary>Jawaban</summary>

Lint memeriksa apakah file valid dan rapi. Kontrak yang menghapus field `saldo` tetap valid. Yang menangkapnya adalah perbandingan dengan kontrak sebelumnya, seperti `oasdiff breaking` di rekaman.

</details>

**3.** Kenapa kontrak OpenAPI berguna saat meminta AI menulis endpoint?

<details class="success">
<summary>Jawaban</summary>

AI mendapat bentuk request, response, dan error yang tepat, bukan tebakan dari deskripsi. Hasilnya juga bisa dicek: response kode AI harus cocok dengan kontrak.

</details>

## Saat me-review kode AI, cek ini

- [ ] Perubahan endpoint disertai perubahan `openapi.yaml` di pull request yang sama.
- [ ] Tidak ada field response yang dihapus, diganti nama, atau diganti tipe tanpa rencana expand-contract.
- [ ] Field baru di request bersifat opsional, atau ada versi minimum app yang sudah naik.
- [ ] Error didokumentasikan dengan skema yang sama (RFC 9457), termasuk extension member.
