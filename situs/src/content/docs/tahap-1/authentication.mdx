## Inti

Authentication menjawab satu pertanyaan di setiap request: siapa yang mengirimnya?

<Rantai data={authn} ringkas />

Budi mengirim password sekali, saat login. Server membalas token acak yang berlaku 8 jam dan hanya menyimpan SHA-256 token itu di tabel `sesi`. Setiap request berikutnya membawa token di header `Authorization`, dan server mencari hash-nya untuk tahu akun pengirimnya.

Di [[t1-m5]], bagian ini sudah benar: server tahu persis bahwa yang bertanya adalah Dimas. Yang tidak ada adalah pertanyaan kedua, "boleh apa?". Itu authorization, di halaman berikutnya.

### Kenapa ini ada

HTTP tidak mengingat request sebelumnya. Request kedua dari HP Budi tiba tanpa tanda bahwa HP yang sama baru saja login. Server harus menanyakan "siapa kamu?" lagi di setiap request.

Dua jawaban naif sama-sama gagal. Mengirim password di setiap request berarti app menyimpan password di HP, dan password ikut tercatat kalau ditaruh di URL. Mempercayai nomor akun dari app berarti siapa pun yang mengganti angka bisa mengaku sebagai orang lain.

Kalau kamu pernah memasang interceptor di [dio](https://pub.dev/packages/dio) yang menambah header `Authorization` ke setiap request, kamu sudah memegang separuh mekanisme ini. Halaman ini membahas separuh lainnya: apa yang server lakukan dengan header itu.

### Cara kerjanya

**1. Password disimpan sebagai hash yang sengaja lambat.** Tabel `akun` menyimpan hash bcrypt, bukan password. Kelambatannya membuat setiap tebakan password dari tabel yang bocor butuh waktu, sehingga menebak jutaan password jadi lama. Lab memakai `bcrypt.DefaultCost`, yaitu 10, sama dengan batas minimum OWASP.

OWASP kini menempatkan Argon2id sebagai pilihan pertama dan bcrypt untuk sistem lama ([OWASP: Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)). Penggantian ke Argon2id ditunda ke Tahap 2, bersama batas percobaan login.

**2. Gagal login tidak membocorkan apa pun.** Password salah dan email yang tidak terdaftar mendapat jawaban yang sama persis. Untuk email yang tidak ada, service tetap menjalankan bcrypt terhadap hash palsu, supaya lama jawabannya tidak berbeda jauh.

<Snippet file="labs/api-t1/output/login.txt" lines="10:20" title="Rekaman lab: labs/api-t1/output/login.txt" />

**3. Token acak, yang disimpan hash-nya.** Service membuat token dari 32 byte `crypto/rand`, yaitu 256 bit. OWASP meminta minimal 64 bit entropi ([OWASP: Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)). Database hanya menyimpan SHA-256 token, jadi isi tabel `sesi` yang bocor tidak bisa dipakai sebagai token.

<Snippet file="labs/api-t1/output/login.txt" lines="22:27" title="Rekaman lab: labs/api-t1/output/login.txt" />

**4. Setiap request diperiksa di satu tempat.** Fungsi `wajibLogin` membungkus semua endpoint yang butuh login. Kalau header kosong atau sesinya tidak ada, ia menjawab 401 dan endpoint di belakangnya tidak pernah jalan.

<Snippet file="labs/api-t1/internal/handler/handler.go" region="wajib-login" lang="go" title="labs/api-t1/internal/handler/handler.go" />

Header `WWW-Authenticate: Bearer error="invalid_token"` mengikuti RFC 6750. Kode `invalid_token` berarti token kedaluwarsa, dicabut, atau rusak, dengan status 401 ([RFC 6750 §3.1](https://www.rfc-editor.org/rfc/rfc6750.html#section-3.1)). Akun pemilik sesi disimpan di context request, dan handler membacanya lewat `peminta(r)`, bukan dari URL.

<Snippet file="labs/api-t1/output/login.txt" lines="30:41" title="Rekaman lab: labs/api-t1/output/login.txt" />

**5. Logout dan batas waktu ditegakkan server.** Query sesi hanya menerima baris dengan `kedaluwarsa > now`, jadi sesi mati sendiri setelah 8 jam. Logout menghapus barisnya, dan token yang sama langsung ditolak:

<Snippet file="labs/api-t1/output/login.txt" lines="43:58" title="Rekaman lab: labs/api-t1/output/login.txt" />

**Sesi di server, atau JWT.** JWT adalah token yang membawa data, mis. `sub` dan `exp`, plus signature. Server memeriksanya dengan menghitung ulang signature, tanpa query ke database ([RFC 7519](https://www.rfc-editor.org/rfc/rfc7519.html)). Isi payload hanya base64url, jadi siapa pun bisa membacanya; signature hanya mencegahnya diubah.

Akibatnya, JWT yang sudah terbit tetap lolos pemeriksaan sampai `exp`, walau user sudah logout. Rekeningo v1 memakai sesi acak di server. Alasannya ditulis sebagai ADR 8 di [[t1-idor]].

### Di stack lain

**Skenario:** memeriksa bukti login di setiap request. Tab Go dijalankan di lab. Tab lain tidak dijalankan, hanya dicek ke dokumentasi.

Yang sama di semua stack: bukti dibawa di header atau cookie, diperiksa sebelum handler, dan punya batas umur. Yang berbeda: apakah server menyimpan sesinya, dan apakah sesi berakhir sendiri.

### Trade-off: cara membawa bukti login

| Pilihan | Kelebihan | Kekurangan | Cocok saat |
|---|---|---|---|
| Sesi acak di database (Rekeningo v1) | Logout dan cabut akses langsung berlaku | Satu query per request; server kedua harus memakai database sesi yang sama | Satu backend, satu database |
| JWT tanpa refresh token | Diperiksa tanpa query | Token curian berlaku sampai `exp` dan sulit dicabut | Umur token sangat pendek dan risiko kecil |
| JWT pendek + refresh token di server | Tanpa query untuk request biasa, tetap bisa dicabut lewat refresh token | Dua jenis token; app harus menangani refresh | Banyak service memeriksa token yang sama |

Asumsi naskah: puncak Tahap 1 adalah 0,14 request per detik. Satu query sesi per request tidak jadi beban di angka itu, sedangkan "logout langsung berlaku" dibutuhkan sejak hari pertama.

### Sengaja belum dilakukan

| Yang ditunda | Kenapa ditunda | Kapan dibuka lagi |
|---|---|---|
| Batas percobaan login | 100 penguji di satu gedung, password dibagikan admin | Tahap 2, bersama brute force |
| Argon2id menggantikan bcrypt | bcrypt cost 10 masih di atas batas minimum OWASP | Tahap 2 |
| Batas waktu idle | Batas absolut 8 jam sudah ada | Belum dijadwalkan; risikonya dicatat di [[t1-fitur-login]] |
| JWT dan refresh token | Tidak ada service kedua yang memeriksa token | Tahap 4 (ADR 8 di [[t1-idor]]) |

### Cek diri

**1.** Isi tabel `sesi` bocor: kolom `akun_id`, `token_hash`, dan `kedaluwarsa`. Bisakah penyerang memakai sesi Budi?

<details class="success">
<summary>Jawaban</summary>

Tidak. Header `Authorization` harus berisi token asli, dan yang bocor hanya SHA-256-nya. Token itu 256 bit acak, jadi menebak token dari hash-nya tidak mungkin dalam waktu yang masuk akal.

</details>

**2.** Di M5, Dimas login dengan akunnya sendiri lalu membaca saldo akun 418. Apakah authentication gagal?

<details class="success">
<summary>Jawaban</summary>

Tidak. Authentication bekerja: server tahu request itu dari Dimas, akun 417. Yang tidak ada adalah pemeriksaan apakah akun 418 milik Dimas. Itu authorization.

</details>

**3.** Budi menekan Keluar. Dengan sesi di server, kapan token di HP-nya berhenti berlaku? Bagaimana kalau token itu JWT 15 menit tanpa daftar cabut?

<details class="success">
<summary>Jawaban</summary>

Sesi di server: langsung, karena barisnya dihapus dan query berikutnya tidak menemukan apa pun (rekaman lab bagian E). JWT tanpa daftar cabut: token tetap lolos pemeriksaan signature sampai `exp`, paling lama 15 menit lagi.

</details>

### Saat me-review kode AI, cek ini

- [ ] Password disimpan dengan hash lambat (Argon2id, scrypt, bcrypt), bukan teks atau SHA-256 polos.
- [ ] `bcrypt.GenerateFromPassword` di Go menolak password lebih dari 72 byte (`ErrPasswordTooLong`); panjang password dibatasi di validasi.
- [ ] Pesan login gagal sama untuk "email tidak ada" dan "password salah".
- [ ] Token dari generator acak kriptografis (`crypto/rand`), bukan `math/rand` atau waktu.
- [ ] Token dikirim di header `Authorization`, tidak pernah di URL.
- [ ] Pemeriksaan sesi ada di satu middleware, dan pemilik request dibaca dari sesi, bukan dari body atau URL.
- [ ] Ada batas waktu dan logout yang mematikan sesi di server.
