## Inti

Database utama penuh oleh query baca. Tahap ini mengajarkan cara berpikir dan trade-off, bukan angka kapasitas.

<WidgetLama nama="arsitektur" tahap={5} />

## Ceritanya

Metric menunjukkan database utama sibuk melayani query baca. Laporan bulanan merchant membuat transaksi harian ikut melambat.

Feed promo dan notifikasi dikirim ke ratusan ribu user sekaligus. Tagihan cloud naik, dan Sinta mulai bertanya soal biaya per transaksi.

## Angka di tahap ini

| Besaran | Nilai | Cara hitung |
|---|---|---|
| User terdaftar | 1.000.000 | asumsi |
| User aktif harian (DAU) | 200.000 | 1.000.000 × 20% (asumsi) |
| Request per hari | 12 juta | 200.000 × 60 request (asumsi) |
| Puncak request per detik | ±1.400 | 12 juta ÷ 86.400 × 10 (asumsi) |
| Data transaksi per tahun | ±44 GB | 200.000 × 2 transaksi × 365 × 300 B (asumsi) |
| File per tahun | ±3,6 TB | 20.000 upload per hari × 500 KB × 365 (asumsi) |

Angka ini tidak menjawab "butuh berapa server". Jawaban itu hanya datang dari load test di sistemmu sendiri.

## Sengaja belum dilakukan, bahkan di tahap ini

- **Sharding database.** Partitioning dan read replica dicoba dulu. Sharding mengubah hampir semua query dan sulit dibatalkan.
- **Menulis ulang ke bahasa lain demi performa.** Bottleneck jarang ada di bahasa pemrograman.
