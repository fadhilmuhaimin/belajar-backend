## Inti

Backend adalah program di server milik tim. Ia menyimpan data bersama, menegakkan aturan bisnis, dan menghubungi sistem lain. App boleh mengecek apa saja, tapi keputusan akhir ada di backend.

## Lihat sendiri

Fitur pertama Rekeningo adalah transfer saldo. Untuk setiap tugas di bawah, tebak siapa yang mengerjakannya, lalu cek.

## Kenapa ini ada

Hari pertama proyek. Raka menulis daftar kebutuhan transfer di papan tulis. Sebagai mobile engineer, naluri pertamanya adalah menaruh semuanya di app. Saldo disimpan di HP, lalu dicek sebelum tombol Kirim aktif.

Lalu Raka membayangkan tiga orang:

- **Budi** memakai HP dan tablet. Saldo di dua perangkat harus sama.
- **Ani** harus melihat uang masuk di HP-nya sendiri, padahal HP Budi tidak tahu HP Ani.
- **User iseng** bisa memodifikasi APK atau mengirim request langsung dengan alat seperti curl, tanpa lewat app.

<WidgetLama nama="hp" src="data/a1-hp.json" />

Di Android, kamu terbiasa dengan Room atau sqflite sebagai sumber data. Itu benar untuk **satu perangkat**. Backend adalah sumber data untuk **semua perangkat dan semua orang**, dan satu-satunya tempat yang tidak bisa diubah oleh user.

Di Tahap 1, backend Rekeningo adalah satu monolith: satu aplikasi yang memuat semua fitur dan di-deploy sebagai satu unit.

Backend Rekeningo punya empat tugas:

1. **Source of truth untuk data bersama.** Saldo, riwayat, dan pesanan disimpan di satu database. Semua perangkat membaca dari sana.
2. **Aturan bisnis yang tidak bisa dilewati.** "Saldo harus cukup" dicek di server. App boleh mengecek lebih dulu, tapi hanya untuk memberi kabar cepat.
3. **Identitas dan izin.** Backend tahu siapa yang mengirim request (authentication) dan apa yang boleh ia lakukan (authorization). Dibahas di [[B5.1]] dan [[B5.3]].
4. **Penghubung ke sistem lain.** Notifikasi ke HP Ani, bank untuk top-up, email struk. HP tidak memegang secret untuk sistem-sistem itu.

Di dalam API ada tiga lapisan. **Handler** mengurus HTTP. **Logika bisnis** memegang aturan Rekeningo. **Akses data** berbicara dengan database.

Pemisahan ini dibahas di [[B7.1]]. Untuk sekarang, cukup tahu bahwa aturan uang tidak ditulis di handler.

## Di stack lain

Keempat tugas di atas sama di semua stack. Yang berbeda adalah di mana kamu menulisnya.

| Stack | Aturan bisnis ditulis di | Izin "hanya data sendiri" ditulis di |
|---|---|---|
| Go, Node.js, Laravel, Django, Spring | Kode aplikasi di server (lapisan logika bisnis) | Kode aplikasi: query memakai id user dari token |
| Supabase | Fungsi SQL di database, atau Edge Function | Policy RLS di tabel |
| Firebase | Cloud Functions | Security Rules |

Supabase dan Firebase tetap punya "backend". Bedanya, sebagian besar sudah jadi, dan aturanmu ditulis dalam bentuk yang berbeda. Itu topik [[A4]].

## Trade-off: kapan pakai apa

| Pilihan | Kelebihan | Kekurangan | Pakai saat |
|---|---|---|---|
| Cek hanya di app | Paling cepat dibuat | Bisa dilewati | Hanya untuk hal tampilan, bukan aturan |
| Cek hanya di backend | Aman | User baru tahu salah setelah request kembali | Aturan yang butuh data server, mis. saldo cukup |
| Cek di app **dan** backend | Aman dan responsif | Aturan ditulis dua kali | Validasi format: nominal, nomor HP |

## Cek diri

**1.** App Rekeningo menyembunyikan tombol "Lihat riwayat Ani" dari Budi. Apakah data Ani sudah aman?

<details class="success">
<summary>Jawaban</summary>

Belum. Budi bisa mengirim request `GET /akun/ani/riwayat` tanpa lewat app. Backend harus menolaknya karena token milik Budi, bukan Ani.

</details>

**2.** Jelaskan kenapa saldo tidak cukup disimpan di sqflite HP Budi.

<details class="success">
<summary>Jawaban</summary>

Pertama, Budi punya dua perangkat, dan sqflite tidak berbagi data antar-perangkat. Kedua, Ani harus melihat uang masuk di HP-nya. Ketiga, data di HP bisa diubah pemiliknya. Semua itu butuh satu source of truth yang dipegang tim: database di backend.

</details>

**3.** Siapa yang memanggil layanan push untuk memberi tahu Ani?

<details class="success">
<summary>Jawaban</summary>

Backend. Hanya backend yang tahu penerima transfer dan menyimpan API key layanan push.

</details>

## Saat me-review kode AI, cek ini

- [ ] Setiap aturan bisnis yang dicek di app juga dicek di backend.
- [ ] Endpoint tidak percaya nilai dari client untuk hal yang bisa dihitung server, mis. saldo atau harga.
- [ ] Secret (API key bank, layanan push) hanya ada di server, tidak di kode app.
- [ ] Aturan uang tidak ditulis di handler, tapi di lapisan logika bisnis.
